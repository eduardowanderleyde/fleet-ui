Críticos: resolver antes do teste no CIn

crítico

Qualquer pessoa na rede pode mover o robô

segurança · backend
O que é
O backend escuta em 0.0.0.0:8000 e a tela em 0.0.0.0:5173, sem nenhuma autenticação. No Wi-Fi do laboratório, quem abrir http://<IP do PC>:5173 tem a tela completa.
Evidência
Teste ao vivo pelo IP de rede do PC (192.168.0.157): /api/status e a tela respondem HTTP 200, e POST /api/go_to_point foi aceito sem login (HTTP 200, alvo na posição atual, nada se moveu).
Correção
Escutar só em 127.0.0.1 por padrão (backend e Vite), com uma opção explícita para abrir à rede. O proxy da tela já usa localhost, então nada mais muda.
crítico

Tela servida pelo servidor de desenvolvimento, com falha conhecida

segurança · frontend
O que é
O Docker roda npm run dev --host 0.0.0.0: é o servidor de desenvolvimento do Vite, exposto na rede. A versão instalada (8.2.1) tem falha de severidade alta no recurso “abrir no editor”, que pode executar comandos.
Evidência
npm audit: 3 altas (vite, undici, source-map-js). Ao vivo, /__open-in-editor responde HTTP 200 pelo IP de rede.
Correção
npm audit fix (atualiza o Vite dentro da série 8) e servir a tela compilada (vite build) em vez do modo de desenvolvimento, restrita a localhost como no item anterior.

Altos: validade do experimento

alto

Controlador diferente do usado no artigo

experimento · Nav2
O que é
O TurtleBot4 no Humble, usado no artigo, navega com o controlador DWB. No Jazzy, usado pelo Fleet UI, o padrão é o MPPI, que é aleatório e pode dar ré.
Evidência
Comparação dos nav2.yaml: Humble dwb_core::DWBLocalPlanner, sem ré (min_vel_x 0); Jazzy MPPIController com vx_min −0,35. A velocidade máxima é a mesma (0,26 m/s no suavizador), por isso a simulação deu 0,248 m/s.
Correção
No make robot-up, usar o DWB com os parâmetros do Humble. O Jazzy ainda traz o DWB, então é configuração.
alto

O script que executa os experimentos não tem testes

testes
O que é
experiment_repeatability.py, que roda toda gravação e todo replay, inclusive os do CIn, tem 0% de cobertura. O coletor de dados também está em 0%. Foram verificados só rodando a simulação.
Evidência
Medição com coverage sobre a suíte inteira (tabela abaixo).
Correção
Testes de unidade para as partes puras (montagem de comandos, métricas do bag, decisão de sucesso e falha) e um teste de ponta a ponta com o robô falso.

Médios

médio

Nome de rota vira caminho de arquivo sem validação

segurança · backend e orquestrador
O que é
/api/save_route_waypoints e o nome de rota de run_config → start_record viram routes/<robô>/<nome>.yaml sem checagem. Um nome com ../ grava fora da pasta de rotas. /api/route_poses já valida com _SAFE_NAME.
Correção
Aplicar a mesma validação ([A-Za-z0-9_-]+) em todo lugar que recebe nome de rota ou de robô.
médio

Ordem de subida depende de esperas fixas

Docker
O que é
Os serviços esperam 18 s e 22 s fixos e não há healthcheck. Num PC mais lento, como o do laboratório, algo pode subir antes do que depende dele.
Correção
Esperar por prontidão de verdade (nós ativos, serviço respondendo) em vez de tempo fixo.
médio

“■ Parar” leva cerca de 3 s

backend · segurança operacional
O que é
Cada comando ROS do backend abre um processo ros2 novo (1,2 a 3,2 s medidos). Com o robô falso, ele andou cerca de 80 cm depois do clique.
Correção
Cancelar pela conexão ROS que o backend já mantém aberta, em milissegundos.
médio

Contêineres rodam como root

Docker
O que é
Arquivos criados nas pastas compartilhadas ficam com dono root (já aconteceu com collections/cbsoft).
Correção
Rodar com o usuário do host, como os alvos cbsoft-csv e cbsoft-analise já fazem.
médio

CI instala dependências diferentes do Docker

CI
O que é
O CI usa requirements.txt (faixas) e o Docker usa requirements.lock.txt (versões fixas). O resultado do CI não pôde ser conferido daqui: o repositório é privado e o gh não está instalado.
Correção
O CI instalar o mesmo arquivo travado.

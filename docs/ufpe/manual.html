Antes de começar

  • Ubuntu 22.04 serve. Não é preciso instalar ROS no computador: tudo roda dentro de um contêiner com Ubuntu 24.04 e ROS 2 Jazzy.
  • Uns 15 GB livres em disco e internet boa na primeira vez (o download é grande).
  • Acesso ao repositório no GitHub. Ele é privado: peçam ao Eduardo para adicionar a conta de vocês como colaboradoras.
1−75 dBm

Instalar o Docker

Use o Docker oficial. Os pacotes antigos docker.io e docker-compose do Ubuntu não servem.

sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker $USER
Depois do último comando, saiam da sessão e entrem de novo (ou reiniciem). Para conferir, docker run hello-world deve funcionar sem sudo.
2−82 dBm

Baixar e montar

git clone -b new-way-samsung https://github.com/eduardowanderleyde/fleet-ui.git ~/fleet-ui
cd ~/fleet-ui
make docker-build   # só na primeira vez: 15 a 30 min

O -b new-way-samsung é importante: é o ramo com o percurso de vocês. Sem ele, vem uma versão antiga. Como o repositório é privado, o GitHub pede login: usem gh auth login ou um token de acesso, porque a senha da conta não funciona no git clone.

Sem GitHub: se o Eduardo entregou o arquivo fleet-ui-ufpe-….zip, descompactem e entrem na pasta. O resto é igual:
unzip fleet-ui-ufpe-*.zip -d ~
cd ~/fleet-ui
make docker-build
3−88 dBm

Ligar a simulação

cd ~/fleet-ui
make cbsoft-up

Esse terminal fica ocupado mostrando o que está acontecendo; deixem aberto. Em cerca de 1 minuto, abram http://localhost:5173 no navegador.

O robô aparece no START de vocês, num salão aberto com coordenadas iguais às do mapa hall_cin_v4. A simulação usa o domínio ROS 42, para nunca conversar com um TurtleBot4 de verdade que esteja na mesma rede (eles usam o domínio 0).

4−93 dBm

Rodar o percurso pela tela

  1. Cliquem em Conectar robô, deixem marcado Custom (simulação local) e cliquem em Conectar. Isso só confirma que a tela está falando com o servidor; não procura Bluetooth. As opções “TurtleBot3 · em breve” ainda não funcionam.
  2. Cliquem em ▶ Executar replay. O robô percorre os 96 m em cerca de 6,5 minutos, gravando os sensores.
  3. No fim, o painel da direita mostra Sucesso, a distância e a velocidade média.
Para repetir uma corrida, parem o terminal do passo 3 com Ctrl+C e rodem make cbsoft-up de novo (cerca de 1 min). O robô volta ao START. A volta automática pela tela existe, mas ainda não foi validada numa rota deste tamanho.
5−97 dBm

Ou rodar o script original de vocês

Com a simulação ligada, num segundo terminal:

cd ~/fleet-ui
make cbsoft-run

Roda o nav_3points.py sem nenhuma alteração de coordenadas e grava o CSV de sempre em fleet_ws/collections/cbsoft/. Em duas corridas assim, o robô andou 96,3 e 96,5 m a 0,254 e 0,253 m/s, em 382 e 383 s.

6−101 dBm

Gerar o gráfico de RSSI

Os scripts de vocês (sync_rssi_nav.py e analise_agregados.py) estão em fleet_ws/scripts/cbsoft/analise/. O replay pela tela grava em MCAP; primeiro, convertam para o mesmo CSV do nav_3points.py:

make cbsoft-csv   # pega a gravação mais recente

Depois, coloquem o log do nRF Connect dentro de fleet_ws/collections/ e rodem:

make cbsoft-analise NAV=collections/cbsoft/<navegacao>.csv NRF="collections/cbsoft/nrf/<log>.txt"

O PNG sai ao lado do CSV. Os horários do CSV usam o fuso do computador, para casar com o log do celular.

Um detalhe no script de vocês

O nav_3points.py assina /amcl_pose com o QoS padrão (VOLATILE). O AMCL publica essa pose como TRANSIENT_LOCAL e só republica quando o robô se move. Por isso, as primeiras linhas do CSV podem sair com pose (0, 0).

Aconteceu numa das seis corridas: a homogênea 1, de 19/05 às 15:57, com 3 linhas em (0, 0). Descartando essas linhas, a distância até desconectar dá 68,6 m, contra 68,4 m no artigo. O resultado publicado não foi afetado.

Para as próximas corridas, assinar com a mesma durabilidade do AMCL resolve:

from rclpy.qos import QoSProfile, DurabilityPolicy, ReliabilityPolicy

amcl_qos = QoSProfile(depth=1,
                      durability=DurabilityPolicy.TRANSIENT_LOCAL,
                      reliability=ReliabilityPolicy.RELIABLE)
self.create_subscription(PoseWithCovarianceStamped, "/amcl_pose",
                         self.pose_callback, amcl_qos)

Percurso e análise

Percurso reproduzido, botão de execução, conversão para CSV e scripts de análise de vocês funcionando.

a testar

Instalação na máquina de vocês

Docker no Ubuntu 22.04 e o primeiro make docker-build.

a testar no robô

Jazzy conversando com Humble

As actions do Nav2 mudaram entre as versões, então o Nav2 roda no PC, do lado do Fleet UI, como no setup de vocês. O robô só manda laser, odometria e TF e recebe velocidade; essas mensagens são idênticas no Humble e no Jazzy.

a fazer

Leitura BLE no robô

A leitura do Bluetooth a bordo do robô real ainda não está integrada ao Fleet UI.

Primeiro passo no dia: a checagem pré-voo

Com o robô ligado e na mesma rede, antes de mover qualquer coisa:

cd ~/fleet-ui
make robot-check   # domínio 0 e CycloneDDS, como o robô de vocês

Ela só escuta, não publica nada. Confere os nós do robô, os tópicos /scan, /odom, /tf e /tf_static, as taxas, o TF odom → base_link e a defasagem de relógio entre robô e PC, os mesmos problemas do guia de troubleshooting de vocês. Também avisa se já há um Nav2 rodando, que precisa ser desligado antes do Nav2 do Fleet UI subir.

Depois: ligar o Fleet UI no robô

Com a checagem toda OK, desliguem o Nav2 que vocês costumam subir no Docker de vocês (ele é Humble e não conversa com o do Fleet UI) e rodem:

make robot-up

Sobe no PC o mapa hall_cin_v4, o AMCL com o robô no START e o Nav2, sem simulação, no domínio e middleware do robô. A tela abre no mesmo endereço, http://localhost:5173. Se o robô não estiver exatamente no START, ajustem a pose inicial: make robot-up X_POSE=… Y_POSE=… YAW=….

Testamos tudo isso com um robô falso, que publica laser, odometria e TF como o TurtleBot4: a checagem passou, o Nav2 subiu e um deslocamento de 1 m terminou com sucesso. O teste com o robô de verdade é o que falta.

Segurança. Na primeira vez, deixem o robô com espaço livre em volta e alguém perto dele. O botão ■ Parar da tela cancela a navegação, mas leva cerca de 3 s para o robô parar (ele anda ainda uns 80 cm): numa emergência, a parada é física. Comecem com um deslocamento curto antes do percurso de 96 m. O roteiro do dia tem o passo a passo completo.
?ajuda

Se algo der errado

“permission denied” ao rodar docker

O usuário ainda não está no grupo docker. Saiam da sessão e entrem de novo depois do usermod do passo 1.

O terminal repete “list of world names” sem parar

O servidor do Gazebo caiu na subida. Parem com Ctrl+C e rodem:

make docker-down
make cbsoft-up
A página em localhost:5173 não abre

Esperem o terminal do passo 3 mostrar o servidor pronto (cerca de 1 min). Se a porta estiver ocupada por outro programa, fechem esse programa e subam de novo.

O robô parou no meio ou o Nav2 abortou

Reiniciem com Ctrl+C e make cbsoft-up. Se acontecer sempre, mandem para o Eduardo a saída de make docker-logs.

Alguém da rede também usa o domínio 42

Escolham outro número:

make cbsoft-up CBSOFT_DOMAIN=57
